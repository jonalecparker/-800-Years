# Session — 2026-08-05: a way to walk around the thing

*Covers 2026-08-04 → 08-05 — one session across the date line.*

## Goal

The user's framing: *"our goal lately has been to get building to a point where we could walk around the castle to see how it felt. I had doubts about whether we were on the right path and you recommended we get to this point before making any changes."* Building is there. What was missing was a pair of legs.

So: a **build mode / walk mode** toggle, with ordinary WASD + mouselook. Everything else this session came out of playtesting it.

## What we did

- **`Assets/Scripts/WalkMode.cs`** (new, on `Main Camera`) — `Tab` toggles. A `CharacterController` is added at runtime with its capsule hung *below* the lens (`centre.y = -0.8` of a 1.8m body), so the camera reads as eyes 1.7m over the feet. No player rig in the scene, no reparenting per toggle, and no capsule in the world at all in build mode. Body radius 0.35m (fits a 1.1m doorway, keeps the lens off the masonry), step offset 0.55m (clears a 0.5m foundation step, walks 0.22m treads), slope limit 55°, gravity −18, a modest hop for getting unstuck.
- **Standing the build systems down** — one static `WalkMode.Active`, read by `FreeFlyCamera`, `GridPlacementSystem` and `BuildMenu`, rather than disabling components. Each holds state a frozen `Update` would strand: `GridPlacementSystem.StandDown()` cancels in-flight gestures, hides ghosts and guides, and calls the new **`CutawayView.Clear()`** — a sliced wall's collider is sliced with it, so a cut castle is one you walk straight through. `BuildMenu` hides its canvas (which takes the `GraphicRaycaster` with it). `FreeFlyCamera.SyncOrientation()` is new because the fly camera keeps yaw/pitch in its own fields and has to be told what the walk did to them.
- **Build mode resumes where the walk ended**, not where it started — so noticing a wall is wrong and reaching for the tool happen in the same place.
- **Walk mode carries its own readout**, deliberately *not* in `ModifierHints` — same precedent as the cutaway: that panel reports what the tool in hand reads, and this is a mode switch.
- **`WallRoom` stair wells, resized** — see "Bugs hit". `Headroom` is now 3m of clear air measured under the deck's **soffit**, plus a new `WellLead` of 1m further down the run, and the opening arc is counted **in treads** rather than along the straight line between the stair's ends.
- **Performance pass** (`ProjectSettings/QualitySettings.asset`, `Assets/Settings/HDRP Performant.asset`, `Assets/OutdoorsScene.unity`) — VSync off on all three quality levels, active level → **Performant**, and SSAO / subsurface scattering / decals / distortion / motion vectors off in the Performant HDRP asset. Camera AA **TAA → FXAA**. Render-target memory on an empty scene: **922 MB → 415 MB (−55%)**.

## Decisions & trade-offs

- **The walker IS the camera.** A capsule hung below the lens rather than a player object the camera parents to. Cheaper in scene structure and in toggle cost; the price is that eye height is baked into the controller's `center` and changing one means changing both.
- **One flag, not component enable/disable.** Disabling `GridPlacementSystem` would freeze a half-drawn gesture and leave a ghost standing in the air and the cutaway still slicing colliders. Standing down is deliberate work, not an absence of work.
- **You land under the camera** on entering walk mode, not along the view ray. Predictable beats clever: a ray would drop you somewhere you weren't pointing every time the camera happened to be level.
- **Escape belongs to the Unity editor.** It was briefly a second way to exit walk mode; that turned out to be the bug (below). Tab is the only toggle.
- **Wells are deliberately oversized and no longer computed tight** (user's call): *"I don't think we need to calculate the well each time, just make it always be enough to accommodate the player's height + a meter or so, it can be bigger than necessary."* A stairwell larger than it needs to be costs a little deck nobody stands on; one a few centimetres too small costs a head, every climb.
- **TAA → FXAA** was not on the approved list but was forced by it: motion vectors can't be disabled while the camera runs temporal AA. Taken because TAA's temporal accumulation is largely wasted over a compressed remote session. Bonus: TAA was the actual cause of the screenshot smearing `CLAUDE.md` attributes to motion blur — there is no MotionBlur component in the volume profile at all.
- **Only the Performant HDRP asset was touched.** `HDRP High Fidelity` and `HDRP Balanced` are untouched so the quality dropdown still gives the full renderer for the eventual art-pipeline lighting pass. VSync is off on all three, though — deliberately, so it can't return by switching preset.

## Dead ends

Nearly all of them mine, on the mouse-look bug. Four attempted fixes shipped and were reverted:

1. **Re-assert `Cursor.lockState = Locked` every frame.** No-op: Unity applies the lock only when the state *changes*, so assigning `Locked` when it already believes it's locked does nothing — which is exactly when it needs re-applying.
2. **Warp the pointer to screen centre, skip that frame's look.** Warped *and* read `Mouse.delta`, double-counting; dragged the camera. User caught it.
3. **Detect drift against last frame's pointer position, bounce `None`→`Locked`.** The threshold was 2px *per frame*, so a slow deliberate turn at high framerate never tripped it and crept to the screen edge anyway. Wrong quantity measured, not wrong amount.
4. **Manual capture: park the pointer at centre and read the look from position rather than delta.** Fixed the double-count but introduced a systematic round-trip error each frame — a constant delta in a constant direction, i.e. the camera spinning into a blur. This is the one where the user said *"I've never had this issue before, I feel like it is something simple we are overlooking"* — and was right.

Reverted to the ordinary implementation (`CursorLockMode.Locked` + `Mouse.delta`). **The root cause was environmental: the user is on Remote Desktop.** [Unity issue tracker: `Mouse.delta` returns zero against a screen edge under RDP.](https://issuetracker.unity3d.com/issues/mouse-dot-delta-returns-zero-when-moving-the-cursor-against-the-screen-edge-when-using-a-remote-desktop-connection) The OS stops delivering movement events at the edge and the lock doesn't physically confine the cursor. **Not fixable in code; accepted.**

Also wrong and corrected mid-session: I told the user `supportedLitShaderMode: 2` meant Forward *and* Deferred. It's `DeferredOnly` (Both is 3), so two of the four approved performance items were already true.

## Bugs hit

- **Stair wells were too low to walk through** (user report: *"I hit my head and can't go through"*). Measured on the live castle: **all four wells gave 1.70m of clear head against a 1.80m body** — systemic, not one bad stair. `Headroom = 2f` was measured to the deck's **top** while the deck is 0.3m thick, so it promised 2m and delivered 1.7m.
  - Fixing the constant wasn't enough. The opening arc was computed along the straight line between the stair's ends, but **a stair is not a ramp**: the tread you stand on is up to a full riser above that line, and a body at the hole's edge stands on the tread under its *leading* foot with its skull still under the deck. Measured a body wedged with `gap=0.05` against the soffit, just short of the opening.
  - Now counted in treads, measured to the soffit, with generous constants.
- **Escape defocused the Game view.** It was a second way to exit walk mode; the Unity editor also uses it to take the cursor back, and *an unfocused Game view has no cursor state applied to it at all* — neither the lock nor the hide. So leaving by Escape and returning by Tab put you in walk mode with a loose pointer every time. Almost certainly the original wall, which I then walked past for three attempts chasing delta. A worse compounding: my `Application.isFocused` guard made `HoldCursor` return early precisely in the state it needed to recover from, so the one path out was the one path never taken.
- **My own diagnostic advice was worthless.** I told the user an invisible cursor proved the lock was holding; `Cursor.visible = false` is set explicitly either way. Corrected, and replaced with an on-screen readout of `held / pointer / centre / look / yaw` — which is what finally produced the decisive data (`pointer` pinned at `789,439` while the physical cursor ended up at the side of the screen).

Self-inflicted, worth remembering:

- Two automated walk tests reported failure that was the test's fault, not the code's: one started the capsule **outside the room** (`foot.x - 0.8` is past the wall's inner face), another built the room, stair and walk **in a single `execute_code` call** so the colliders hadn't synced and the body walked through everything. A third "failure" was the test walking up the stair, across the deck and *off the unparapeted roof edge* — 28m of walking intent on an 8.25m stair. Track the peak, not the endpoint.
- The first head-clearance profile measured against a linear ramp and reported a comfortable 2.20m at the exact arc where the body was actually wedged with 0.05m.

## Verification status

**Hand-tested by the user:** walk mode itself, and the wells — *"wells are perfect now."* The mouse is accepted as an RDP limitation.

**Not hand-confirmed:** whether the performance changes helped. My frame timings were taken with the editor in the background, where Unity throttles it, so the 100ms/334ms figures are that throttle and not real frame times. The render-target reduction (922 → 502 → 415 MB) *is* measured and real. `sync_interval` still read `1` after disabling VSync — **restart the editor before judging it.**

**Automated, driven through the real graph in play mode:**

- Walk mode entry grounds the camera exactly at ground + eye height; 10m of walking intent into a wall stopped at z −175.89 = the face plus body radius plus skin; the build HUD hides; the stand-down runs once and latches; no live ghosts left.
- Wells after the fix, on a 4.45m storey rise and a 1.62m one: both bodies reach the deck (peak feet 13.49 vs deck 13.45), and an upward ray from the top of the skull **never finds deck within 6m** at any point of either climb.
- Doorways measured at 2.10m clear head — already fine for a 1.8m walker, untouched.

## Open at end of session

- **Roof decks have no parapet.** The test body walked up the stair, across the deck and straight off the edge — the deck is flush with the wall tops. Honest graybox behaviour rather than a bug, but it's a real thing to feel now that you can stand on it. Crenellations are already on the procedural-detailing list.
- **The build → walk → fix loop destroys the castle every time.** The wall graph is play-mode only, so every code fix domain-reloads and takes the runtime build with it. This bit three times this session. A save/load for the graph may be worth pulling forward now that there's a reason to keep a castle standing between edits.
- **Builds still default to High Fidelity.** `m_PerPlatformDefaultQuality` for Standalone is untouched — there's no scripting API for it and hand-editing the YAML would be overwritten from memory on quit. Arguably the behaviour you want (light editor, full-fidelity build for art judgement), but it's an inconsistency.
- **`CLAUDE.md`'s motion-blur screenshot note is probably obsolete** — it was TAA ghosting, and the camera is on FXAA now. Confirm on the next capture and update the note.
- **The real performance read isn't available over RDP.** If it matters for a real decision later — judging whether the art pipeline's lighting pass is affordable — that needs a local session or a build run at the machine.
- Node posts still have no collider (only wall sections, stair treads and slabs do), so you can lean into the quarter-barrel at an outside corner. Visual clip, not a hole; adding one would change what the *cursor* hits too.
- Walk speeds (2.8 / 6 m/s) are public fields on the component and untuned by feel.
- The centre-castle playtest is *still* unfinished, now across four sessions.

# Session — 2026-08-05 (second): the near arc, and a castle that survives

## Goal

Two halves. First a **design session** (user narrates, Claude organizes): long-standing doubts about whether the freeform builder can yield a *realistic* castle game, and the biggest worry — editing an inhabited castle without being homeless while the rebuild takes in-game time. Second, the first step of what that session decided: **the castle save/load system**.

## What we did

**Design (recorded in the docs, not code):**

- The homelessness worry turned out never to have been recorded — and the design doc still called the builder grid-based, which was stale (full freeform is the decided direction). Both fixed in `medieval-castle-lord.md`: fidelity marked SUPERSEDED with the surviving reasoning kept, the worry recorded under Castle Building with its likely shape (plan layer / work orders — *likely, not decided*), and open questions #15 (deferred homelessness) and #16 (the lord's income) added.
- **DECIDED: defer the inhabited-castle question** until the rest of the game imposes real constraints. Standing rule so the door stays open: **no new system may assume construction is instantaneous in the world.**
- **The near arc, agreed** (`Docs/Roadmap.md`): 1. castle save/load (promoted to prerequisite), 2. real European terrain (~1m national LiDAR, one site one tile), 3. the permanent castle built and walked on that hill, 4. economy design session + 1220-landowner research pass, 5. procedural town. Structural support stays deferred (user's call, again).

**Code — `Assets/Scripts/CastleSave.cs` (new), near-arc step 1:**

- JSON serializer for the whole graph: nodes (point, baseY, radius), edges (node refs, control, heights, skirt, openings, roomBuilt), stairs (baked spans), rooms (ring by edge index, floorY/roofY/roofNote, outlines, wells by stair index). Never meshes — sections, treads, posts and slabs rebuild through the same `Rebuild` paths a commit uses.
- **`WallRoom.Restore`** (new) — the counterpart of `Create` that asks the world *nothing*: floorY, roofY, roofNote, both outlines and the wells arrive stored, honouring the written-at-the-moment doctrine (no `RaiseSills`, no `TryBuildRoof`, no `NotifyStairBuilt` on load). Only slab meshes are re-derived. New accessors `HasFloorSlab` / `Outline` / `DeckOutline` for the save; `WallStair.baseStep`/`baseWallHeight` made public for the round-trip.
- **F5 save / F9 load** in `GridPlacementSystem.Update` — build mode only (loading swaps the world out from under a walker); F9 stands the tool down first so no gesture points at destroyed objects. `Saves/castle.json` at project root; results in the BuildLog; out of `ModifierHints` per the cutaway precedent.
- Load is **not a graph mutation**: `WallEdge.Create`, never `CommitEdge` — no splits, no crossings, no room hooks. The save came from a legal graph; restoring it wholesale re-creates exactly that graph.

## Decisions & trade-offs

- **Identity is positional** — a node/edge's id is its index in the file; rooms and wells reference by index. Nothing needs identity that survives *across* saves yet, and a save is a complete graph, so within-file indices are all the stability required.
- **`-Infinity` travels as a `-1e30` sentinel** — JSON has no infinity and JsonUtility's handling of one isn't worth trusting across Unity versions. Applies to baseY, fixedTopY, sill, baseFrom.
- **Terrain mismatch warns but loads anyway** — the terrain name is stored; walls keep their curves and re-foot on whatever ground is there. Saves made before the terrain import are throwaway by design.
- **`Saves/` at project root, not persistentDataPath** — visible, diffable test saves; real save slots move when the game has a front end. Deliberately *not* gitignored: the permanent castle save is precisely the kind of artifact to commit.

## Bugs hit / infrastructure

- **The UnityMCP tools were missing from the session entirely** — the server was registered for the TestingAI and 400 Years projects but never for this one. Registered (`claude mcp add --transport http UnityMCP http://127.0.0.1:8080/mcp`); future sessions get the tools natively. This session drove the bridge over raw JSON-RPC HTTP from PowerShell instead (helper preserved in the memory note `unity-mcp-bridge-recovery`).
- One test-side false alarm: the first liveness test asserted a tee adds exactly one ring edge, but its geometry crossed a *second* ring wall on the way in — ring 5→7 with both splits re-pointed is correct behaviour. Re-run with clean geometry: pass.

## Verification status

**Hand-tested by the user** ("awesome save is working well") — the `Saves/castle.json` in this commit is their save, kept deliberately.

**Automated, in play mode through the real graph:**

- Built a castle exercising every stored fact: lock-top square room (designated, roofed), curved terrain-following wall T-ing in, doorways with default and raised sills, floor-to-roof stair with its well, skirted second-storey wall.
- A 15-field fingerprint (sections, section-top sums, sills, arcs, controls, wells, ring sizes, slab flags, step counts) was **identical** before save and after load; second load idempotent.
- The loaded graph stays live: a new tee split a restored ring wall and the ring re-pointed and stayed closed; deleting a restored room wall breached the room.
- Zero console errors or warnings throughout. Test save deleted after.
