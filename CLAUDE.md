## The wall graph (2026-07-29)

The wall system is a **node/edge graph** (`Docs/WallGraphRebuild.md` was the brief; it shipped 2026-07-29). Relationships are **stored, never inferred** — the old physics-probe machinery (junction bands, graze lanes, cut planes/ClipRow, the 10° gate, IsBlocked, buildOrder asymmetry, ignore lists, end extensions, Links, hasGaps) is deleted, not dormant. Don't reintroduce inference; every structural question is a graph question.

- **Model**: `WallNode` (point + member list) and `WallEdge` (exactly two nodes + quadratic Bézier `control`, height data, sections). `WallGraph` (static) is the ONLY mutator: `CommitEdge`, `CommitCourse`, `DeleteSections`, `SplitEdgeAtMany`. Edges meet only at nodes and never overlap or cross — illegal states are unrepresentable. An edge's geometry depends on nothing but its own nodes/control/heights/terrain, so **nothing ever rebuilds because a neighbour changed** (only node posts remesh).
- **Placement is graph editing** (`GridPlacementSystem`, name kept for scene refs): click = node, drag = edge. **Straight walls CHAIN** (2026-08-09): a commit re-anchors the gesture on its own end node (carrying storey/height/snap state; Esc ends the chain, walls stay), and each leg records its created edges (`WallChainLeg` — host splits are deliberately NOT in the list, so a right-click leg-undo deletes only what the leg built, never what it crossed; a leg later split by another leg undoes partially — accepted, the delete tool covers it). Snaps resolve to nodes: `TryNodeSnap` (any node within 0.75m), then `TryFlankSnap` (mid-edge **centerline** point; commit splits the host there — a T at any angle, host end zones ±0.9m excluded). Free ends get 1-valent nodes. **Crossings auto-split**: `FindCrossings` (polyline intersection, no physics) → each becomes a shared 4-way node — both walls split via exact polar-form subdivision (`SubCurve`), gold post ghosts preview the pending joints. Crossings within 0.35m of a gesture end collapse into the end's node; within 0.3m of an existing node they reuse it (chain-through).
- **The never-cross-into-a-building law, the floor step and the partition tell are DEAD, not dormant** (killed 2026-08-08 by the building rebuild — they shipped 08-07 and lived a day). All three existed to guess which storey a terrain-storey gesture meant against a terrain-storey building. Buildings now stand on foundation slabs, so their walls live on a slab storey the terrain gesture's per-base planar graph never meets — the ambiguity those laws policed is unrepresentable. Consequence to watch in playtests: a terrain wall drags through a slab-borne building's space unimpeded (different storeys never interact); if that needs law, it's a new design, not a revival of `TryBuildingLanding`.
- **The one refusal left** (`OverlapsExisting`, whole ghost red): a near-exact redraw along an existing wall — <3° relative tangent, <0.15m centerline distance, sustained >0.6m. Everything else is legal: shallow V's, flush parallels, drags across a flank anchor's host (now just a T + crossing, no more red).
- **Nodes own all joints** (`WallNode.RebuildMesh`, the old wedge rule promoted to sole renderer): implicit post radius = half thickness, member inward bearings sorted, each gap exposes gap−180° of arc. Valence 1 = nothing (the edge's flat cap IS the finished end — free ends and delete-hole boundaries cap flat), collinear butt = nothing, L = quarter barrel, 90° T/X = flush (zero exposed arc), shallow tee = one shoulder arc. Flank members no longer exist — a T splits the host so ALL members are end members. Posts read end-section spans; an upper-storey wall has its own nodes, so its corners grow their own posts with no stack-climbing special case.
- **Storeys are `baseY`, not a separate kind of object** (2026-08-02): stacked courses are **deleted, not dormant** — `stackBase`, `IsCourse`, `CreateCourse`, `BuildCourseSpecs`, `UncoveredRanges`, `CommitCourse`, `RebuildStackOver`, `StackTopOver` and the post stack-climb are all gone. A wall standing on another wall's top (or on a slab) is an ordinary edge with its own nodes, so it can be a member of a room's ring — which a course never could, since `FaceAt` can't trace a non-member. That was the reason to cut them, not tidiness. **Wall top faces are build surfaces, and stacking has no free direction** (2026-08-02): both cursor resolvers — `TryGetCurveTarget` (wall tool) and `TryGetBuildSurface` (room / circle / rect) — report `hoverBaseY = section.topY` on a top-face hit and set `hoverRideHost`. **A run anchored on a wall top is a SPAN of the wall below, never a direction**: `RideOnto` puts the point on the host's centerline and pulls it to the host's own ends within `endpointSnapRadius`, the drag end slides along that host whatever the cursor is over, and `TryRideControl` gives the edge the host's exact curve via `WallGraph.SubCurve`. Nothing overrides it — not the bulge wheel, not Shift, not R (the hover stub takes the host's bearing). The click-stub is a span of the host too (`BuildRideStubPreview`, slid INWARD to fit): centred on a point that pulls to the host's own end, it hung half a thickness of masonry off the cap. **Alt is the only way out**, and it clears `hoverRideHost` while keeping the storey. Both were added because a second storey that can wander off its own foundations is not a storey. Building on a *slab* stays free-form; the lock is wall tops only. **The one thing a ride still snaps to is a node on its own storey** (`RideDragEnd`, 2026-08-02): two upper walls built from opposite ends have to close on ONE node, and a node already sits on the centerline the run is locked to, so honouring it costs the lock nothing — the walk re-runs to the node's exact point with the end-pull suppressed (`rideExact`, or it would slide past the node onto the host's cap) and is discarded unless the chain actually lands within 0.15m of it. **A ride also adopts the host's height** like every other snap: without it, crossing a wall's top edge with the cursor flipped the ghost between the dialed height and the host's, because grazing the SIDE adopts and standing on TOP didn't.
- **A ride follows the masonry THROUGH its nodes** (`RideChainEnd`, 2026-08-02): it used to clamp at the host's ends, so a circle (8 quadratic arcs — 4 would bulge 6% off a true circle, 8 is 0.3%, so the segment count is right) took eight drags to stack and a room took four. The walk consumes a host, takes the **straightest continuation on the same storey** out of the far node (`StraightestContinuation`, dot > 0.2 so it never doubles back; a T upstairs picks the run that carries on), and stops where the cursor's nearest point falls mid-host. An anchor sitting ON a node retries the walk through the node's *other* member, or dragging backwards off a node would do nothing. Each span still becomes its own edge with its host's exact curve (`BuildRidePreview` → one `pendingCommits` entry per span, committed in order so they meet at shared nodes) — **`pendingCommit` is a LIST now**, and every gesture goes through it.
- **A snapped point can be standing on a wall too** (`RideHostUnder`, 2026-08-02): the ride lock used to be reachable only by a top-face raycast, so snapping to the END of a short second storey (the ray hits that wall's *side*, no top face involved) handed back free direction exactly where a player goes to extend it. Both snap branches now call `AdoptRideHostUnder`, which asks the geometric question — an edge of another storey, within half a thickness of the point in XZ, whose section-top RANGE brackets this base. Range, not the top at that parameter: an unlocked wall's top steps down a slope. Nothing stores what rests on what (structural rules stay deferred), so this is asked in exactly two places — that snap, and `StackFit`. Slab hits are exempt (`slabTile != null`), which is what keeps slab building free-form.
- **A stacked wall's bottom is `baseY − skirt`, and only `baseY` is the storey** (2026-08-02): an unlocked host's top steps with the terrain, so a flat bottom at the hovered section's top left an open slot over every lower step. `StackFit` buries the joint — `skirt` = base − lowest covered host top — and pins `fixedTopY` to clear the HIGHEST covered top by the dialed height (measuring from the hovered section instead would sink the run into its own host when you anchor low on a slope; on a level host the two numbers are equal and nothing changes). `WallEdge.skirt` is geometry ONLY: `baseY` remains node identity and every planar-query filter, so a skirted wall still welds to its unskirted neighbours. `EdgeParams.skirt` defaults to 0, which is always safe; surgery copies it. Applies to the wall tool and the room chain, **not** to circle/rect (those build one shared `EdgeParams` for the whole figure).
- **Delete is edge surgery** (`DeleteSections`): kept section ranges → sub-edges; a mid-hole makes two new 1-valent tip nodes; a fully-deleted edge detaches and empty nodes dissolve (`OnMemberGone`). No linked rebuilds, no gap flags — survivors were never derived from the dead.
- Assists: length stepping relative to the anchor (`lengthStep` 0.5, Alt frees); direction is **fully free everywhere** — Shift steps it in `angleStep` 5° increments (absolute bearings on free drags, **measured from the face normal** on flank-anchored drags, so a lazy Shift-drag off a face lands exactly 90° flush); snapped-height adoption (anchor > drag-end > hover; Ctrl+scroll overrides via `heightOverride`); lock-top; distance guides; angle arc; Offset tool (commits through `CommitEdge`, so it splits what it crosses); `C` tangent-tied connector (only when both snapped ends have a single outward direction — valence-1 node or flank). **Shift means angle stepping and nothing else, in the wall tool and the room chain alike** (2026-08-01): it outranks a flank landing — the stepped bearing wins and the run probes `SteppedLandingReach` (2m) past the cursor to MEET the host, landing on its centerline at the stepped angle (`TrySteppedLanding` in the wall tool, the crossing clamp in room mode). 1m is not enough: `FindCrossings` drops crossings within 0.35m of the probe's own end. Approaches under ~40° can't reach and stay free — honest, not silent. Node snaps still outrank Shift (only one of a point and an angle can be honoured), and the **tangent-tied connector moved to the `C` key** to free Shift for this. Node-snap hovers highlight the members' existing end sections gold (no stub, no post markers — posts preview only at pending crossing points); a bare click on a node commits nothing.

## Vertical math is spans, not layers

- `WallEdgeSection.bottomY/topY` is the source of truth. Never assume uniform section height or ground at y=0 (terrain exists; slice ground = min of sampled corners, quantized down by `baseStep`).
- Bulge (0.5m) and foundation bases (0.5m) are deliberately **stepped** so separately-built structures align — don't make those continuous. **The height exception is closed** (2026-08-08, the quarter-grid unification, the user's call): `CurrentWallHeight` **quantizes to `heightScrollRate`** (0.25m) so the dial LANDS on the quarter grid rather than merely moving by it (fractional trackpad notches accumulate in `heightMultiplier`; the getter rounds), and slab planes seat on the same lattice (`SlabTile.FloorStep` 0.25 — masonry footings stay on the half-metre `baseStep` by the stepped-foundation doctrine). Footing (0.5 grid) + height (0.25 grid) puts every free-built TOP on the quarter lattice, which is what lets one building's roof meet another's floor by scrolling instead of luck. **Snapped adoption still copies exact heights** — matching a neighbour IS alignment and beats the grid, so legacy off-grid walls are matched, never rounded. A **locked-top host matches by top elevation**, not stored height (`SnapHeightOf` = `fixedTopY` − the wall's own floor: terrain at the snap for a ground wall, `baseY` for a stacked one — measuring a storey's height from the terrain beneath it is nonsense, and the skirt is not height), and `fixedTopY` survives splits.
- **Two elevation readouts serve the rendezvous** (2026-08-08): the height panel appends `GhostTopY` — the ABSOLUTE elevation the active ghost's top lands at, set by every preview builder from the SAME numbers the commit writes (ghost = commit extends to the readout; set BEFORE each builder's cache early-return, because the field clears every frame; on an unlocked terrain run it reports the top at the ANCHOR cell, the number you dial against). Below it, `InspectLine` reports what the cursor is over as **stored** planes — a slab tile gives its kind and top plane, a wall gives its hovered section's `topY`, terrain gives ground — never hit-point geometry, so the cutaway's sliced colliders can't misreport. Purely readouts: no tool logic reads either, and they stay out of `ModifierHints` (that panel is keys, not numbers).

## Buildings: foundations, walls, floors (2026-08-08)

The room system was rebuilt bottom-up (`Docs/BuildingRebuild.md` was the brief; it shipped 2026-08-08, same day — and the slab half was redrawn from tiles to outlines that same evening). Buildings are authored from four kinds of object — **foundation slabs, walls, floor slabs, roofs (decorative, later)** — and **no plane is ever inferred**. The derivation machinery is **deleted, not dormant**: `WallRoom` entirely (designated rings, `BuildFloor`, the crown vote, `TryBuildRoof`, `CarriedToPlane`, wells, `RaiseSills`/`FloorServing`, all the Notify hooks), Designate, `roomBuilt` provenance, and the room-mode crown gates (`GroundAbove`). Don't reintroduce derived planes; the player states them.

- **Slabs are DRAWN OUTLINES, not tiles** (2026-08-08, the user's call after hand-testing: square tiles over an irregular room can't floor it — "it felt right when i was able to draw the room shape via the walls"). `SlabTile` (name kept for scene/save refs) is a **polygon prism**: `verts` (world XZ, stored CCW) + `topY`/`bottomY`/`isFoundation`, built as a **world-space mesh on a unit transform** (the wall convention — the old Y-scale build died with the tiles) with a MeshCollider for cursor rays and the walker's feet. Both tools (`ToolMode.Foundation`/`Floor`, `UpdateSlab`; the menu's Room category still holds Foundation / Wall / Floor in build order) are **the chain gesture the walls taught**: click corners, close on the first corner (`endpointSnapRadius`), the polygon fills as ONE prism (`SlabTile.BuildPrism`, ear-clip `Triangulate` — handles concave; a tangled outline refuses). Esc abandons the outline; a corner click needs 0.25m from the last. Polygon predicates (`SignedArea`/`Contains`/`SelfIntersects`/`PolyOverlaps`) live on `SlabTile`, static, shared by ghost and commit. Same-kind overlap at the same plane refuses — abutting/shared edges are legal contact, strict interior overlap is not. The mesh renders 2mm proud of the stored plane (same-facing coplanar z-fight vs wall tops); **stored planes stay exact** — planes match by data, not pixels. R and tile-size dials are gone; corner snapping replaced tile abutment (`TrySlabOutlineSnap`: existing same-kind outline corners 0.5m, then edges 0.4m). **The Circle/Rectangle CHECKBOXES arm stamped foundations** (2026-08-15, the user's call — the SAME `Shape` state the walls read, one set of checkboxes for everything; an R-cycle shipped and was removed the same day): rect = 3 clicks, circle = centre → radius as a 24-gon, both through the chain's plane machinery and `CommitSlabPoly` (the one commit door for every slab gesture). The outline chain (foundations AND floors) Shift-steps leg bearings and shows the corner arc — snaps and the closing pull outrank Shift, per doctrine; `SetShape` must cancel the slab gesture like every other.
- **ONE outline, ONE plane — the ANCHOR states it** (`ResolveFoundationPoint`): a snapped anchor adopts the host outline's plane (matching a neighbour IS alignment and beats the grid — extending a level is snapping to it), a free anchor seats at its own ground ceiled to the quarter grid, **plus the dial: Ctrl+scroll moves a foundation's plane in `FloorStep` (0.25m) steps** (`HandleSlabPlaneScroll` — pre-anchor as an offset, mid-chain directly; this is the "player states the plane" made literal). The whole chain holds the anchor's plane. TWO laws bound it, live on the ghost as **the same test the closing click runs — `SlabPolyRefusal` returns the refusal STRING, so the red ghost and the log line are one fact** (one-test doctrine): buried (ground above the plane over >50% of the polygon's area, sampled by `SamplePolyGround`) and skirt (lowest ground more than `SlabTile.MaxSkirt` = 2m below the plane). Machine-verified consequence: a 20m square on a 6m slope refuses at EVERY plane — buried low, stilted high — which is the design saying **terrace**: split into two foundations at their own quarter-grid planes. Dips never refuse; the skirt spans them (`FoundationBottom`, unchanged convention). Mid-draw red is honest, not blocking — only the CLOSING click is gated, so an outline may pass through a red tentative state on its way to a legal shape.
- **A floor outline exists only by CONNECTION** (`ResolveFloorPoint`): the anchor must take its plane from a hovered wall top (cut-surface guarded like every top-face read) or an existing floor. **After the anchor the cursor maps onto the PLANE itself** (the ray meets y = plane), so the outline crosses open air, doorways, anything — and corners snap to **wall nodes carrying masonry at the plane** (`TryFloorNodeSnap`, end-section `topY` within 0.2m — flooring a room is clicking its corners) and to existing floor outlines at the plane. No free-floating floors; Alt only disables snaps. **A stairwell is drawn AROUND — or STAMPED** (wells returned 2026-08-09, as stored facts this time): `SlabTile.Well` is a polygon hole through a floor slab with a stored OWNER (`WallStair`), stamped at commit time (floor drawn over a stair, or stair committed under a floor), never re-derived; deleting the stair heals the floor (the delete tool's job). Foundations never carry wells. `SlabTile.Rebuild()` re-meshes in place from STORED facts, never the transform (the cutaway may be slicing that very slab), and **re-cooks the MeshCollider forced-enabled** — a disabled MeshCollider skips its re-bake silently and stays ray-transparent forever after re-enabling. Known limit: hand-drawn edges are straight, so curved rooms floor chorded — the eventual answer is a trace-STAMP (Enclosure runs once at click time, emits an ordinary stored polygon, no live derivation), deliberately deferred.
- **A slab is a build surface** exactly as room decks were: both resolvers treat a `SlabTile` hit as elevated ground (`hoverBaseY = topY`), building on it is free-form (the `AdoptRideHostUnder` deck exemption is `slabTile != null` now). **Walls hug its rim** (2026-08-09, `TrySlabRimSnap`): on a slab hit — top face OR side, a ray just past the rim hits the skirt and still means this slab (`hoverSlabTile`) — the point pulls to the outline inset half a wall thickness, so the wall's OUTER face lies exactly on the slab edge; grabs anchor and drag end, wall tool and room chain alike, and yields to Shift's stepping like the flank. **A TERRAIN hit within rim reach adopts the slab too** (`RimSlabFromTerrain`, 2026-08-10): a near-grade pad (the free-anchor default) exposes no skirt for the ray to catch, and a terraced pad's uphill rim sits flush with or under the hillside — so without this, the grab zone outside the outline didn't exist exactly where foundations usually stand (the user's first hand-test caught it). Nearest plane within `RimAdoptBand` (MaxSkirt + 1m — the hillside just outside a lawful pad can drop past MaxSkirt inside the grab radius) wins; the adoption is wholesale (same storey flip as pointing at the top face, in both resolvers), and Alt keeps terrain meaning terrain. Consequence, accepted for consistency with direct slab hits: terrain-storey masonry within the ≤0.75m rim band loses the hover to the rim. Consequence worth its own sentence: **building walls stand on a FLAT plane, so every section bottoms exactly at the slab** (verified) — footing-stepping and skirts remain only under terrain walls, and a doorway's sill is simply the wall's own ground (`doorSill = ground`).
- **Enclosure is a CHECKED fact, not a built one** (`Enclosure`, the lean survivor — `RingArea`/`RingContains`/`SignedArea` moved there from WallRoom; `FaceAt` uses them). The Room tool is now just the chain gesture (clamping, ghosts, closure all unchanged); closing traces the face and ANNOUNCES it in the BuildLog — "Room enclosed — N walls on the Xm floor" on a slab storey, "a yard" on terrain. Roomness becomes stored gameplay state when the economy needs it, not before.
- **Deferred by the brief, deliberately**: support rules (a floor must connect same-height walls, ~20m unsupported span cap), decorative roofs, wedge tiles for round footprints, and any law for terrain walls passing through slab-borne buildings.
- **THE DEVIATION LAW** (`TerrainPads.MaxDeviation`, 3m — user tuned 2m → 5m → 3m across 08-07; it's one global number, never per-tool): ground may never differ from the **pristine** heightmap (cached at first use) by more than the law — enforced per-sample inside `TerrainPads.Reshape`, measured against PRISTINE not current ground, so repeated carving can't creep (verified: re-benching 20m deep bottoms out exactly at pristine−law). The law governs the Ground tool alone (buildings never move earth) — but the **one-test doctrine it minted is general**: any commit-time refusal must be warned live by running the SAME test (never approximate: a lines-only check once warned nothing where the commit refused, 08-07; the foundation burial gate follows the doctrine). Ops are **permanent** (deleting a building doesn't un-dig; Restore is the undo), edit a **runtime clone** of the TerrainData (play-mode writes to the asset silently persist — never touch it), and stop short (`KeepOut`) of existing walls, whose footings never resample. The plain wall tool moves no earth. Economy prices the labor later; the law is the pre-economy balance AND the siege-era protection (no moats, no cliff-carving).
- **The Ground tool** (menu button, two jobs): **Path** — circular draped brush cursor while aiming, then a drag benches between the two ends' ground, any grade, law-clamped mid-run; **Shift holds the anchor's height instead — a LEVEL path** (Shift's angle-stepping doctrine is scoped to the wall tool and room chain; the Ground tool reads no angles, so the key was free). **The drag deforms the REAL terrain live and commits only on release; Esc puts the hill back** (2026-08-07): `TerrainPads.PreviewBench` snapshots the post-ops heightmap on first call, reverts-then-reapplies as the endpoint moves (throttled to ≥0.25m of travel), and a commit is `CancelPreview` + the ordinary `Bench` — the same door, so preview and commit cannot differ. End heights sample `PrePreviewGroundAt` (the snapshot), NEVER live ground — the bench deforms the ground under both its own ends, so live sampling feeds the preview back into itself; the anchor's height is captured at the click for the same reason. `ResetToPristine` drops the preview snapshot (a load mid-drag would revert onto stale heights). The two-tone ribbon (blue FILL / red CUT) rides the deformed surface and classifies against the snapshot too. Bench end heights are stored in the op — replay never re-asks. **Restore** — a hold-and-sweep PAINT brush: ground returns to pristine under the brush as it moves, the terrain itself being the preview; each swept span records one op. Inherently abuse-proof — its only power is undoing. Terrain-only raycast (`TryGetTerrainPoint` accepts `TerrainCollider` hits alone, which also satisfies the cut-surface rule by type). **Ctrl+scroll sizes the tool in hand** (`HandleGroundSizeScroll`, 0.5m/notch: path width 1.5–10m, brush radius 1.5–12m) — same Ctrl branch of the wheel arbitration as wall height, per mode. **Reshaped ground repaints itself**: `TerrainPads.RefreshSurface` recomputes the slope-derived grass/dirt alphamap over each touched region (reads `TerrainGenerator.dirtSlope*`), and `ResetToPristine` restores the cached pristine alphamap too — a cut scarp shows worn earth, a restored face gets its old paint back. The **level-area** job stays on the wishlist (2026-08-07), though foundations now cover most of what it was for.

## Stairs, doorways, the cutaway (2026-08-04)

Briefs: `Docs/Stairs.md` and `Docs/Doors.md` hold the *why*; they move in here once playtested and become history. Only the cross-cutting constraints are below.

- **A stair is a rider (`WallStair`), a doorway is edge data (`WallEdge.Opening`)** — and the split is deliberate. A stair belongs to two storeys, so it gets its own object, its own `All` registry, and membership of no `WallNode`: it never splits a wall, no wall splits it, and no planar query sees it. A doorway is a hole in ONE wall's masonry, so it lives on the data the sections derive from and the doctrine holds. Don't promote a doorway to a rider (it could only cut its hole by inference) or demote a stair to a `WallEdge` variant (it would need an `isStair` flag every query filters out).
- **Every mutator that makes sub-edges must call `WallEdge.CarryDetails`** — both surgery sites in `WallGraph`. It carries BOTH kinds of edge data (openings and buttresses) in one pass so the sub-edge rebuilds once; the per-kind halves are private. **A buttress is edge data too** (2026-08-16): `WallEdge.Buttress` is `t` (centre parameter, remapped linearly by a split) + `side` (+1/−1, the sign `SideOf` answers with) + `topY` (**absolute**, stated at the click, so re-shaped ground and surgery can't drift it). The BOTTOM is derived, by **THE FOUNDING RULE** (`WallButtress.FootAt`, the user's call 2026-08-16 — and the whole reason no face restriction is needed): **a pier rests on the first solid thing beneath it and runs continuously up from there.** Two cases, and they are NOT one clamp — a level platform (foundation, courtyard, floor deck) under the WHOLE footprint carries it, every corner tested by `SlabTile.Contains`; nothing under it and it goes to the EARTH, `Bury` (0.3m) below the lowest of its own four plan corners, snapped down to `baseStep`, **so all four are under the surface**. `Ground.HeightAt` reads the terrain and CANNOT see slabs, which is why a `Max` against `FloorY` got the platform case right only by accident and the rim case wrong (the pier hung in the air wherever the ground outside was lower — on a terraced pad, everywhere), and why the `Min` that fixed the rim then plunged the platform case through its own floor. Asking what is actually underneath gets both right for the same reason; `FloorY` survives only as a floor for a pad cut INTO a hill. Machine-verified on Grosmont: of 224 face placements on slab-borne walls, 90 rest on a platform and 134 reach the earth — the two faces of the SAME wall giving different answers. A pier the split runs THROUGH doesn't survive, exactly like a doorway. `WallButtress` is only the render part (the `WallEdgeSection` role) and serves BOTH owners — exactly one of `edge` and `node` is set; its dimensions are constants and `TryBuild`/`TryBuildCorner` are the ONE door each kind's ghost and commit go through. Its faces are all mapped with the same UV handedness, which is tidy but NOT what fixed the see-through — see the tangent rule in "Edge geometry". Rooted at the CENTERLINE, not the face: the buried half can't open a gap where a curve bends away, and it isn't priced (`Estate.CostOfButtress` charges the projecting solid less half the weathering wedge, so refund equals charge). **No strength number is stored, deliberately** (the user's call) — a buttress will stiffen a wall when there is a siege to test it, and inventing the figure before its consumer exists is guessing at a balance nothing can check.
- **The Buttress tool** (`ToolMode.Buttress`, bar button): point at a face, click. The wall answers the footing, the face and the top (its own less `SetOff`); **Ctrl+scroll moves the TOP**, stored as a DROP below the wall's own top so it carries meaningfully from wall to wall (an absolute elevation would silently clamp against the next wall along), quarter steps, scroll-up raises, re-adopting the wall's answer at the set-off, latched to the TOOL like the stair's climb. It dials the top and not the pier's height because the footing digs into the ground — overall height counts buried stone and is not a number anyone can aim with. The `MinHeight` floor and the "too little wall" refusal both measure against the wall's own floor (`MasonryFloorAt`), never the buried footing. Two refusals worth their reasons: **an end is not a joint** — where masonry carries straight on (`MasonryContinuesPast`, the doorway's own question) the pier may sit on the joint and overhang it, because a chained run is many edges through no fault of the player's; only a corner, a T or a free end keeps the pier whole on its own side. And **crowding is asked of the WORLD, not the edge** — same storey, same face (compared by outward bearing, so a facing pair across the thickness stays legal), within a pier's width — because the neighbour a foot away usually belongs to the next edge along. A pier across a doorway is refused from either face. **A CLASPING CORNER BUTTRESS BELONGS TO THE NODE** (2026-08-16, `WallNode.Buttress` = `bearing` (world degrees — a stated fact, not a gap index, so it survives members joining and leaving) + absolute `topY`): a pier belonging to two walls at once belongs to neither, and nodes own every joint in this graph. It is the historically characteristic placement (a square keep's angle buttresses) and it was the one the face rules REFUSED, since a face pier is kept clear of real ends. Near a real corner the cursor is claimed by the node (`CornerGrab` 1.6m, comfortably wider than the zone a face pier is refused in, so there is no dead band): `WallNode.TryCornerAt` runs the SAME arithmetic as the wedge mesh — inward member bearings sorted, a gap of g exposing g−180 of arc, `QuoinMinArc` the smallest turn worth dressing — on the CURSOR's own bearing from the node, so standing on the OUTER face of an L gets a clasping block while the inner face falls in a gap with no exposed arc and drops through to an ordinary face pier (verified). `CornerShape` is the face pier's box widened and pushed out by however far the masonry corner sticks out — `reach = (t/2)/sin(turn/2) + Projection`, `halfWidth = Width/2 + (t/2)/tan(turn/2)`, back buried to 90% of the inner corner — so **at a 180° "corner" it degenerates EXACTLY to a face pier with no special case anywhere**, and at 90° both back corners land inside the members' masonry (verified 2 of 2). **ONE block to a corner**: two would stand at the same point and could only intersect. It rebuilds with `WallNode.RebuildMesh` because its plan comes from the turn its members make — a corner that stops being a corner simply renders nothing until one returns. **`TryGetWallSideHit` skips buttress colliders** — the one deliberate exception to first-hit-only, or the wall a pier stands on is untouchable for a metre either side of it; the delete tool checks for a pier FIRST for the same reason, and takes it down whole (one list entry, never a cut).
- **A BATTLEMENT IS A SPAN ON THE EDGE, AND A MERLON ON A JOINT BELONGS TO THE NODE** (2026-08-17). `WallEdge.Crenel` is `t0`/`t1` plus the two dialled numbers (`height`, `gap`) — edge data like a doorway, because the notches are cut in this masonry and no other. A span rather than a per-edge flag (the design call, made before a line was written): a flag can only say "this whole wall", and a chained run is many edges through no fault of the player's, so what a flag meant would depend on where the graph put its nodes. **`WallNode.Crenel` is just a height**: a block sitting on a joint belongs to both walls at once and so to neither — the clasping buttress's rule, this graph's oldest. Its seat and plan are RE-DERIVED from the members every rebuild, and that is right where the pier's absolute top was right: a pier is founded in the ground and must not drift when the ground moves, a merlon SITS ON the wall and must follow wherever its top goes. One block to a node, like the clasping pier.
- **The Crenel tool is THREE PHASES and one drag that FOLLOWS THE MASONRY** (the user's calls, 2026-08-17 — the click-means-the-whole-wall shortcut shipped and was removed the same day, and press-drag-release became press-drag-release-**click**). HOVER rides a single real merlon on the cursor — built by `WallCrenel.TryBuild` from a one-merlon span (`OneMerlonAt`), so what follows the cursor IS a merlon of that wall at the dialled height, not a stand-in — and shows the JOINT's own block where the cursor has snapped to a node. DRAGGING lays the run out. Letting go leaves it **PENDING**: still a ghost, still re-laying out as the dials move, until a second click builds it — because reaching Ctrl and Alt with the mouse button held down is not a thing a hand does. Right-click or Escape abandons at any phase, and a release with a refusal drops back to hovering rather than stranding a red pending run. **The confirming click is taken BEFORE the frame's hover work**, or the same press that builds would first re-aim what it builds.
- **The run snaps to the only two points it has reason to meet exactly** (`SnapCrenelT`, 1.2m of arc): this wall's own end nodes, and the ends of any battlement already standing on it — a parapet stopping a hand's breadth short of the corner is the one mistake this gesture can make that the player cannot see until it is built. Snapped tints the ghost `snapColor`, the tell every other snap in the tool set gives. A drag ending on another wall walks the graph to get there (`EdgePath`, the delete tool's own path finder), so crenellating a whole ward is one gesture. Each leg stands back from every joint by `NodeReach + gap` and the joint gets its own block — verified: the nearest edge merlon's near face sits exactly one dialled embrasure from the block's edge. **A leg too short to hold a merlon after standing back is not an error** — its joints still get theirs and the parapet steps across the short wall as one piece of masonry.
- **Two dials, and they PERSIST** (`Ctrl + scroll` merlon height, 1.2m down to a quarter of it in 0.1m steps; `Alt + scroll` spacing, 0.2–4m). Deliberately NOT re-armed by `SetMode`, unlike the stair's climb and the pier's top: a parapet dialed once is the parapet this castle has, and re-stating it on every wall is work the player already did. **Anchoring on a battlement that already stands adopts ITS height and spacing** (`AdoptCrenelStyleAt`) — on this wall, or through the node the anchor sits on, since starting at a corner means carrying on from whichever wall arrives there — so a run built in two drags reads as one piece of masonry. - **The merlon keeps its width and the EMBRASURES absorb the fit** (`WallCrenel.Layout`): the dialled gap chooses how many blocks a stretch holds, then the spacing divides what is left. **A LONE merlon is CENTRED** — with nothing between, there is no embrasure to absorb the remainder, and laying it from the span's start dumps every millimetre at the far end. That shipped and was caught in playtest as "the chain didn't place flush with the ends even though it snapped to them": a short leg between two joints holds exactly one block, so one corner got the dialled embrasure and the other got the embrasure plus the leftover — measured 0.80m against 1.30m at the two ends of the same 3.93m wall. Centring splits it (1.42m from each end, verified) and both corners read alike; for n ≥ 2 the spacing already absorbs it exactly and the end blocks land ON the span's ends (0.000m, verified). Scaling both to fit instead makes every wall's blocks a slightly different size, which reads as sloppy stonework the moment two walls meet. The COUNT is never stored — the rule is "a whole number of merlons, one at each end", so a span clipped by a split re-lays out still correct at its new corner; a stored phase could drift. **A split CLIPS a battlement, it does not drop it** — the deliberate difference from an opening and a pier (`CarryCrenels` vs `CarryButtresses`): those are single objects with a width, so half of one either side of a node is not what anyone drew, while a crenellated stretch is just a length of wall that happens to be notched. - **Merlons are DECORATION TO THE CURSOR AND ORDINARY STONE TO EVERYTHING ELSE**: all three resolvers skip `WallCrenel` colliders so `section.topY` stays the wall top a floor slab is drawn from — verified 13/13 that a merlon takes a plain raycast while both resolvers still report the wall top. Solidity costs nothing because **walls were never meant to be walkable** (the user's, 2026-08-17): a floor slab spanning two wall tops is the wall-walk, and it has been working well. `WallCrenel` is one object per span (or per node) carrying every block in ONE world-space mesh on a unit transform, so delete is one list entry gone, never a cut; the demolition refund pays back a wall's dressing (`Estate.CostOfDressing`) only when the edge dies WHOLE, since a partial delete carries the battlement onto the survivors. **Winding was got wrong TWICE here** — first all five merlon faces inside-out (the parapet was a hole seen from above), then every side of the joint block. The tell both times was a raycast finding nothing, and the lesson is the LandPlot one: raycasts ignore backfaces, so an inverted face is invisible AND untouchable from the one side that matters. Test orientation per BLOCK against that block's own centre — a run's bounds centre says nothing about which way one merlon faces, and a check against it reports garbage.
- **`WallEdgeSection.openingIndex >= 0` means NOT solid masonry.** A lintel's bottom is the doorway's head, metres up; a threshold's top is its sill. Anything reading `bottomY` as "the ground this wall stands on" must skip them — `MasonryFloorAt` learned it the hard way.
- **A section's footing is a property of the wall's GRID, not of where a section boundary happens to fall.** `BuildSpecs` settles the cell count and each cell's footing from the edge's arc alone, then cuts openings into it. Openings used to re-divide the wall, and since a footing is the lowest ground under a footprint snapped down, longer sections sit lower — cutting a door into a short partition sank the masonry beside it. Windows and arrow slits cut into the same grid.
- **A doorway spanning a step reaches DOWN to the lowest cell it covers and UP to the highest** — threshold meets the ground, lintel meets the wall. One figure for both leaves a notch in the wall top, every time, on the high side.
- **Any raycast reading `hit.normal.y > 0.7f` must ask `CutawayView.IsCutSurface` first.** A sliced wall's exposed cross-section has an upward normal exactly like a real wall top; three resolvers do this, and a fourth that didn't would offer to stack a storey at the wall's real top, metres above what's being pointed at.
- **`CutawayView` slices by transform Y-scale about the object's own bottom** (every mesh here is a vertical prism), so view state stays out of geometry and nothing rebuilds because the cut moved — the collider rides along, which is the whole point: what you can see is what you can hit. **Never read `Renderer.bounds` for a vertical span** — a sliced renderer reports the *slice*, and reading it back switches the cut off one step above wherever it sits. That's what `CutawayPivot`'s cached floats are for — and there are TWO (08-08): `authoredY` AND `authoredScaleY`, because **not every prism is a world-space mesh on a unit transform**. A `SlabTile`'s height is its Y-scale; the old restore-to-scale-1 assumption crushed every tall tile one frame after commit, with no cut even active (the sunken-foundation bug). All span/slice/restore math now multiplies mesh bounds by the authored scale; anything new that renders under `splineParent` must either be a world-space mesh on a unit transform or trust this generalized path — never add a third convention. (Slabs themselves moved to the unit-transform convention that same evening when they became polygon prisms; `authoredScaleY` stays as the guard for whatever scale-built prism comes next.)
- **The stair's length is DERIVED from the rise, so there is no pitch refusal** — don't add one back; it would police a freedom that was never granted. The only refusal is "not enough wall". Door width/head stay fixed (dialing them needs another wheel meaning). **The stair's CLIMB is dialable** (2026-08-09): Ctrl+scroll (`stairRiseDial`, quarter steps, clamped [2 risers, wall top]; at the top it clears — full climb is the default, not a dial position). R cycles flip → perpendicular (one straight span out from the wall, never blocked) → back. **The foot reads what it stands on** (`StairFootRest`): the run's start point samples the highest wall top / floor slab under it (lintels skipped) and adopts it as `baseFrom`, which is what makes half-stair + landing + half-stair compose. Width is 1.8m — and `stairWidth` is scene-serialized, so a script-default change alone does nothing.
- **Room-driven sill raising died with derived rooms** (2026-08-08): a doorway's sill is the wall's own ground — a building wall bottoms at its slab, so the sill is right by construction. `Opening.sill` remains stored on the edge (cut-time capture, `-inf` = the wall's footing). Derived wells died the same day; **stored stamped wells returned 2026-08-09** (see the buildings section — owner on the well, heal on stair delete).

## The world frame and the tile bake (2026-08-15)

The Marches world IS the British National Grid (`Docs/WorldFrame.md` is the brief): world X/Z = BNG easting/northing − (332000, 210000), world Y = metres ODN, 8×8 2km tiles on even-km lines named by grid ref ("Marches [SO4024]"). The old linear-Mercator frame, the source terrain, `TerrainTiler` and `CastleLidar` are DELETED, not dormant. Doctrine:

- **`WorldFrame` (static) is the ONLY door between real-world and world coordinates** — BNG↔world, WGS84↔BNG, the grid-ref namer, and the legacy Mercator chain (migration-only; never use it for new work). Anything georeferenced goes through it or is wrong at England scale.
- **THE TILE IS THE ARTIFACT** (`MarchesBaker`, ContextMenu Bake Tiles): every tile bakes deterministically from BNG source rasters (NRW 2m LIDAR = the base DEM, flight strips MERGED per sample — several files cover one cell with different NODATA holes; OS Terrain 50 fills the rest, both sources BNG+ODN native so there is no reprojection or datum fitting anywhere). Un-do of anything baked = re-bake. Fire it via `EditorApplication.delayCall` through MCP and verify by console state.
- **Resolution follows features**: castle tiles (≤600m of a site) bake 1025, river-crossed tiles (waterway ≥5m) 513, rest 257. Fine edges are PINNED collinear to coarse neighbours (coarsest pins first) plus a corner-consensus pass — geometry cannot crack, but Unity's auto-connect can't stitch LOD across resolutions ("Stop neighboring" console spam is that fact, accepted; use `read_console`'s `filter_text` or the spam drowns everything).
- **Rivers carve INSIDE the bake** from pre-carve in-memory refs that THALWEG-SNAP onto the LIDAR's real channel (the OSM centerline meanders ±5–10m off it; carving the map line cut a braided second trench). Refs + snapped stations are SAVED (`Assets/Terrain/MarchesRiverRefs.json`); the water ribbons and bed splat follow the channel AS-BUILT and refuse loudly on a stale refs file — levels never re-derive from carved ground.
- **`Ground` (static facade) is still the ONLY way scripts read terrain** — `Terrain.activeTerrain` FORBIDDEN outside Ground/TerrainPads; cursor raycasts stay TYPE-based. `TerrainPads` is unchanged (per-tile pristine, world-space ops; the baked carve becomes pristine). `CastleSave` still matches by `Ground.BaseName` (strips at " ["); **v8 migrates pre-v8 Marches saves once** (XZ through the legacy chain, absolute Y + `WorldFrame.LegacyLift`), discriminated by the CURRENT scene being the Marches — Spiš saves never migrate.
- `TerrainSources/` (~1.2GB ASC, gitignored) is the bake's input; the brief records both re-download queries. LIDAR heights are MILLIMETRES, rows start at the NORTH edge, Mono's ZipArchive refuses the NRW zips (`Expand-Archive`).

## The Marches dressing (2026-08-11)

Real land cover for the Marches scene (`Docs/MarchesRealism.md` is the brief): `MarchesDressing` (on the Terrain, ContextMenu Dress / Clear Dressing like TerrainGenerator) bakes `Assets/Terrain/MarchesFeatures.json` — OSM roads/woods/waterways preprocessed OFFLINE into world XZ with the verified georeferencing; Unity never fetches. Roads are **splat paint** on the tiles' 1024 alphamaps (the road ribbons died 2026-08-12 — the user's call), water is **draped ribbons + a distance-swapped HDRP tier** over a carved bed (the rivers bullet below), woods fill with low-poly terrain trees (~32 tris — primitive spheres are ~760 and a quarter-million instances of that is unshippable), bushes hedge the lanes and keep out of the rivers. It is scene DRESSING: nothing joins CastleSave, the root stays out of `splineParent`, ribbons carry no colliders (the walker must not trip on a road), oak trunks do collide.

- **A draped mesh fights the terrain's LOD, not its heightmap**: the rendered ground deviates from `SampleHeight` by `heightmapPixelError`'s worth of screen space, in BOTH directions — a 0.12m lift vanished wholesale at pixelError 5. Dress() pins pixelError 2 and lifts 0.30/0.18; anything new draped on terrain must respect that contract.
- **Ribbon winding is easy to mirror** (the LandPlot lesson again, and it cost a debugging session: probe quads "reproducing" the builder rendered fine while the real chunks were backface-culled — the probe had L/R swapped). When a draped mesh is invisible from above, read the baked normals back FIRST.
- `roadWidths`/`splatCore` etc. are scene-serialized on the component — the `stairWidth` trap: changing a script default does nothing to the existing scene; set the field on the component too.
- **Roads are splat paint ONLY, and only the roads of 1220** (2026-08-12): `castleRoadsOnly` (MarchesDressing, default on) filters the modern OSM density to the pairwise shortest ROUTES between `CastleSite` markers (`CastleRoads` — stitched vertex graph, 2.5m merge, Dijkstra; kept routes paint as through-roads), **trimmed at each castle's grounds boundary** (`CastleGrounds` outlines — the painted road ends at the gate, and the survey's village walk starts there). Splats, hedgerows and tree keep-outs all read the filtered set. The runtime timber planter (`TimberWoods`, survey section) recomputes the same routes for its keep-out — deterministic, so paint and tree gaps agree. **Two road-graph laws, both paid for live (2026-08-15)**: the feature bake must force OSM junction vertices through polyline simplification (ways that join share the literal node, often mid-way along one — simplifying it out of ONE way severs the graph; 800 components, "castles share no road route"), and castles snap to the nearest vertex ON THE LARGEST COMPONENT (OSM keeps genuinely disconnected orphan stubs, and Skenfrith's nearest vertex was one). **Water sits at ref − freeboard, near grade**, floored just above the bed: bed-level water got z-killed at distance when the terrain LOD simplified the sub-cell trench away — and because that LOD error is SCREEN-space, no fixed raise suffices: `RiverWaterLOD` also LIFTS far ribbon chunks by 0.004/m past 250m (cap 8m), zeroed near the camera and on upgrade — a view correction, never baked into meshes. The carve itself lives in the tile bake now (world-frame section above); un-carve = re-bake.
- **Water is two tiers split by distance** (`RiverWaterLOD`, ticks every frame BY DESIGN — a view system like tree LOD, no stand-down): cheap translucent ribbons everywhere — flat at bed + fill, cut wide so edges bury in the banks, chunked by 300m CELL with bake facts on `RiverChunk` — and HDRP `WaterSurface` (River, custom-mesh over the same chunk mesh) within `upgradeRadius`, max 4 active. **HDRP custom-mesh water keeps the mesh's vertex heights** (waterToWorld = identity in the package source — read it before trusting docs) and draws the mesh explicitly, so sloping reaches render sloped and the ribbon renderer disables during an upgrade. The 8m `maxChunkFall` guard is COSMETIC (lake ripples on a torrent), not structural. `supportWater` is on in the HDRP Performant asset. **HDRP's river wave defaults are SEA-sized** (largeWindSpeed 30 — rolling swells, worse the smaller the river): the LOD's Waves dials set brook scale, scaled per chunk by `RiverChunk.maxWidth`. A `RiverbedLayer` (4th splat layer, dark mud, river beats road where they meet) keeps grass from showing through the water; the LOD seam visible from altitude is a KNOWN deferred item (Rivers.md).
- Tier D atmosphere lives in `Assets/Terrain/MarchesSkyFog.asset` — a CLONE of the Sky and Fog profile (the shared asset also drives the Spiš scene; never edit it in place). **Hedgebanks and field mottle (2026-08-15)**: the LIDAR keeps field-boundary earthworks but strips the hedges that explain them, so Dress detects bank crests on the FINE tiles (proud of a 7m ring by `hedgeBankSignal`; coarse tiles skip by construction — the box-average smears banks away) and plants bushes along them, and the grass/dirt splat carries two-octave world-anchored noise (`splatMottle`). Hedge candidates are collected map-wide THEN hash-thinned to `maxHedgeInstances` — a first-come cap spent itself entirely on the southern tiles — and the global `maxTreeInstances` (450k, scene-serialized) needs headroom for hedges + woods or the thinning quietly sparsifies the woods.

## Build mode and walk mode (2026-08-05)

`WalkMode` (on `Main Camera`) puts you on your own feet inside what you drew. `Tab` toggles. It exists to *judge* the builder, which is the only reason any of the above is finished.

- **`WalkMode.Active` is a static flag every per-frame system reads** — `FreeFlyCamera`, `GridPlacementSystem` and `BuildMenu` stand DOWN on it rather than being enable/disabled. Each holds state a frozen `Update` would strand: a half-drawn gesture, a ghost left in the air, a cutaway still slicing. **Any new system that ticks every frame has to decide, in the same commit, whether it stands down** — and standing down is deliberate work, not an absence of it (`GridPlacementSystem.StandDown`).
- **The stand-down MUST clear the cutaway** (`CutawayView.Clear`). The collider rides the slice — that's the feature in build mode and a castle you walk straight through in walk mode.
- **The walker IS the camera**: a runtime `CharacterController` with its capsule hung *below* the lens (`center.y = bodyHeight/2 − eyeHeight`). Eye height is therefore baked into `center`, so changing one means changing both. Added at runtime on purpose — build mode wants no capsule in the world at all.
- **`center` is a LOCAL offset, so the body swings on a pendulum unless it is pinned** (2026-08-16, `WalkMode.PinBody`, called from `Look` and `Enter`). The camera pitches the whole transform, and that rotates the offset: measured at 85° of look-up the capsule stood **0.80m forward of the lens with its feet 0.73m high** (−0.97 instead of −1.70), and looking down swung it the same distance *behind*. So where you could walk depended on where you were looking — and it is a plausible way past an obstruction that stops you when level. The capsule never TILTS (bounds stay 0.70×1.80×0.70 at every pitch; PhysX keeps its own up axis), so countering the rotation on the offset alone is exact — verified (0.00, −0.80, 0.00) at every pitch after, live in the player's own session. Any future rig that hangs a collider off a rotating transform owes the same counter. It was **not** why stairs wouldn't climb (that was the sweep length, above) — it only made that symptom look angle-dependent.
- **A frame's travel must be cut into sweeps smaller than the smallest thing it climbs** (2026-08-17, `WalkMode.MoveSwept`, `MaxSweep` 0.15m): `CharacterController.Move` is ONE discrete sweep, so a move longer than an obstacle can wedge ON it instead of stepping over it. The scene's `walkSpeed` is 10 (script default 2.8) and the editor runs the Game view at ~17 fps, so a frame carried the walker **0.58m into a flight of 0.249m treads — 2.3 treads per sweep** — and it jammed on a tread nose (contact normal y≈0.42: an EDGE, not a face). Measured on Grosmont's 33-step flight, driving the real controller from the foot: one Move/frame **never reached the top** at 17 fps (187 straight stalled frames) and never left the first step at `runSpeed`; capped, it reached the top at every speed and frame rate with zero stalls. Total per-frame displacement is unchanged, so the feel doesn't move. Two lessons paid for live: the stall looked **angle-dependent** (whether a frame lands on a nose or a tread is luck, and turning the head changes the approach enough to shake it loose), which sent the diagnosis chasing the camera for two rounds; and the thing that settled it was a temporary per-frame TRACE in `Step` (keys, wish, distance asked vs distance achieved, grounded, `collisionFlags`, and the flattest-normal contact) — reconstructing the input path in a probe kept proving the climb *worked*, because a probe's dt is whatever the probe loop says it is. **When a probe disagrees with the player, instrument the real path.**
- **Walk mode carries its own readout and stays out of `ModifierHints`** — same precedent as the cutaway: that panel reports what the *tool in hand* reads, and this is a mode switch.
- **Escape belongs to the Unity editor — never take a second meaning for it.** It drops the Game view's focus, and an unfocused Game view has *no* cursor state applied to it, neither lock nor hide. Binding it to "exit walk mode" put you back in with a loose pointer every time.
- **Do not try to fix mouse-look over Remote Desktop.** `Mouse.delta` returns zero against a screen edge and `CursorLockMode.Locked` pins only the *reported* position while the physical cursor roams ([Unity issue tracker](https://issuetracker.unity3d.com/issues/mouse-dot-delta-returns-zero-when-moving-the-cursor-against-the-screen-edge-when-using-a-remote-desktop-connection)). Four fixes were tried and reverted — re-asserting the lock (a no-op unless the state *changes*), warping plus `Mouse.delta` (double-counts), per-frame drift detection (misses a slow creep), and manual centring off position (systematic round-trip error, spins the camera). The implementation is deliberately the ordinary one.

## Save/load (2026-08-05)

`CastleSave` serializes the graph and riders; geometry rebuilds on load. **Saves are named slots** (2026-08-08): a slot is a file in `Saves/` — the NAME is the file name, the DATE is the write time, nothing stored twice. The Saves button (menu bar) opens a modal panel: type a name (filename-safe chars only, `SanitizeSlot` at commit = the same filter the field applies per keystroke), Enter/Save writes it, click a listed slot to load it. `CastleSave.CurrentSlot` is whatever was last saved or loaded, and F5/F9 act on it — the hotkeys never guess. **`BuildMenu.ModalOpen` is a stand-down flag like `WalkMode.Active`**: the panel captures the keyboard (`Keyboard.onTextInput`) for slot names, so `GridPlacementSystem` stands down on it (same block as walk mode — a tool reading R, C and F5 under someone's typing would act on their spelling), `FreeFlyCamera` stands down on it too (WASD is typing as well — added 08-08 after it shipped without), and `WalkMode` ignores Tab while it's open. Each slot row carries a **trashcan** (`CreateSlotDeleteButton` — drawn from rects, the built-in font has no glyph; its raycast target sits on the row's, so the click deletes without loading): `CastleSave.DeleteSlot` removes the file, no confirm, BuildLog announces. A deleted `CurrentSlot` stays current — F5 writes it anew, F9 refuses like any missing file. `StandDown` also clears `InspectLine`/`ghostTopY` now — walk mode hides the HUD but the panel doesn't, and a stale readout under it would report a hover that no longer exists.

- **Schema version 12** (2026-08-17): each edge carries its crenellated SPANS (two parameters plus the dialled height and spacing) and each NODE its joint merlon (a height). The merlon COUNT never travels — it derives from the span, so a save states the stretch and the load lays it out again identically. Pre-v12 saves have none, and a zero height or gap means "the default", so the omitted-field trap is a safe answer here rather than a silent change. v11 (2026-08-16): each NODE carries its clasping corner buttresses (bearing, absolute top). v10: each edge carries its buttresses (parameter, side, absolute top). Pre-v10 saves have none — the list deserializes empty and every wall stands exactly as it did. v9 (2026-08-16): bridges. Version 8 (2026-08-15): records the BNG world frame — a pre-v8 save loading into the Marches (current `Ground.BaseName` "Marches", saved name "Terrain") migrates ONCE: every stored XZ through `WorldFrame`'s legacy Mercator chain, every finite absolute Y + `WorldFrame.LegacyLift`, packed sentinels and relative quantities untouched. Spiš saves never migrate (frames agree in their own scene — the CURRENT scene discriminates, both old terrains were named "Terrain"). v7 (2026-08-12): each parcel carries its `territory` (index into the name-sorted castle-site list); v6 plots migrate once at load by nearest site. v6 (2026-08-10): the survey's parcels, the calendar's `clockDays` and `households` travel (see the survey section). v5 (2026-08-09): the treasury travels (`SaveData.treasury`, pence) and each edge carries its `WallKind` as an int (0 = Stone = both the enum default and what every old wall was). A pre-v5 save grants the fresh-start inheritance (`Estate.StartingPence`) — the version check, not a sentinel, decides. v4 added wells (owner = positional stair index, -1 never heals); v3 (2026-08-08) made slabs drawn polygons; **v2 square tiles still load** (a v2 entry with no verts migrates as the 4-corner outline its center/size/yaw described); version-1 saves refuse cleanly — the user's call was to DELETE those, not migrate. Load/RestoreSnapshot take the palisade material as an optional trailing arg — a caller that omits it gets stone-textured palisades, not an error.
- **`CastleSave` is one door with four handles** (2026-08-09): `Save`/`Load` are file I/O around shared `Capture()`/`Apply()`, and `Snapshot()`/`RestoreSnapshot()` are the same pair in memory — the Delete tool's right-click undo restores a pre-delete snapshot through the exact path a load uses (full fidelity by construction). The snapshot is scoped to the delete-mode session (`SetMode`/`StandDown` clear it) so a stale undo can never roll back later work. Any new stored fact automatically rides the undo because there is only the one Capture.
- **Every new stored fact must join `CastleSave` in the same commit** — a field added to `WallEdge`/`WallStair`/`SlabTile` that isn't serialized silently vanishes on load. This is the serialization face of stored-never-inferred: if it can't be re-derived, it must be saved.
- **Load restores, never re-derives**, and load is NOT a graph mutation: `WallEdge.Create`, never `CommitEdge` — no splits, no crossings, no announcements. The save came from a legal graph; restore it wholesale.
- **`-Infinity` travels as a `-1e30` sentinel** (`Pack`/`Unpack`) — JSON has no infinity. Any new float field with the terrain-sentinel convention must go through them.
- **Earthworks save as typed operations and reapply before masonry** (2026-08-07): `Load` calls `TerrainPads.ResetToPristine()` then `Replay`s each saved op in order (kind 0 pad / 1 bench / 2 restore; bench end-heights are stored, never re-derived), BEFORE any wall is created — footings re-foot on the shaped ground. Older saves' pads deserialize as kind 0 via field defaults. A terrain edit that skips the ops list vanishes on load exactly like an unsaved field.
- Identity is positional (index within the file); nothing needs cross-save identity yet. `Saves/` is deliberately committed — the permanent castle save is a project artifact.
- F5/F9 are build-mode only (loading would swap the world out from under a walker) and stay out of `ModifierHints` by the cutaway precedent; the Saves panel stays out for the same reason (it's a menu, not a tool modifier).

## Elevated ground (proto-storeys)

- Slabs are **build surfaces**: `WallEdge.baseY` (default −∞) raises a section's bottom, and slab hits are detected by the `SlabTile` component on the collider (`topY` is the plane). Any new raycast that can hit a slab must decide deliberately whether it's ground.
- **`EdgeParams` is a struct**: an object initializer that omits `baseY` gets **0, not −∞**. Set it explicitly everywhere, including tests.
- Snaps are storey-filtered (`BaseMatches`) and adopt a host's storey (`AdoptSnapElevation`) — a gesture on a deck must never grab the masonry a storey below. **A null base means the TERRAIN storey, never "any storey"** (2026-08-02): `BaseMatches` is now just `WallGraph.SameBase(edge.baseY, atBase ?? -inf)`, matching what `TrySteppedLanding` already fed `FindCrossings`. Snaps compare XZ alone, so a wall and the wall stacked on it are a dead tie and the wildcard picked between them on float noise — pointing at a ground wall's side within 0.75m of an upper wall's end node (a 1.5m-wide dead zone around every upper end, and node snaps outrank flanks) jumped the hover a storey, where the ride then drew a red ghost along the wall already standing there. Consequences: a node with no member on the filtered storey is skipped outright (`TryNodeSnap`), and a gesture keeps its ANCHOR's storey for the whole drag — the old `shapeBaseY ?? deckY` / `roomChainBaseY ?? deckY` fallbacks are gone, since with terrain-null they'd let a ground rect's side snap onto a deck it happened to run past.
- **The cursor ray names the storey, and a SIDE hit names it too** (`hoverSnapBase`, 2026-08-02): both resolvers set it — the slab/top-face base when there is one, otherwise the base of whatever wall the ray struck, and null (terrain) for terrain. It is NOT `hoverBaseY`: aiming at a ground wall's side means the ground storey while the gesture still stands on the terrain. This is the only thing that can tell a stack's co-located walls apart, so every hover-phase snap takes it instead of `deckY`. A snap onto an elevated wall still carries its storey in through `AdoptSnapElevation`, and from there `AdoptRideHostUnder` still locks the run to the wall below.
- **The planar graph is per-base** (2026-08-02; it used to be height-blind): `WallGraph.SameBase` (0.25m tolerance, −inf = terrain, and −inf never matches a finite base) filters `FindCrossings`, `OverlapsExisting`, `CoincidentCoverage`, `ResolveEndNode`, the distance/alignment guides, and **node identity** — `WallNode` carries its own `baseY` and `FindAt` takes one, because nodes are stored at y=0 and an upper wall's ends land directly above the lower wall's node. Without that they weld and one post tries to render two storeys of joint. **Any new query that compares XZ must take a base.**
- **No structural rules yet, deliberately** (user's call, 2026-08-02): nothing stores what rests on what, so deleting a wall leaves masonry above it hanging in the air. Build without rules first, add them later. `baseY` alone is enough to reconstruct support when that lands — don't add a spatial "what's under me" query in the meantime. The support rules' first real design is sketched in `Docs/BuildingRebuild.md` (same-height connection, span caps), deferred with the roofs.

## Placement state that expires

- **`EffectiveWallHeight` is only meaningful on the hover/click frame** (it reads the live hover snap). Anything a gesture needs later — height, locked-top plane, storey — must be **captured at the anchor click** (`shapeTopY`, `roomChainTopY`, `anchorSnapHeight`). Recomputing mid-drag silently substitutes the HUD height; that bug shipped once and cost a half-step misalignment.
- Ghost/overlay shells must scale about the **mesh bounds center** (`FitShell`), not the transform pivot — some meshes here are world-space on origin-pivoted objects, so pivot scaling translates them metres away.
- `WallGraph.DeleteSections` surgers an edge **once** (survivors are new edges with new indices) — pass all of an edge's doomed indices in a single call via the set overload.

## Edge geometry

- **EVERY runtime mesh wearing the stone material must call `RecalculateTangents()`** (2026-08-16). The material does parallax occlusion mapping, which ray-marches in TANGENT space — and a runtime mesh carries NO tangent stream unless one is asked for, so the march ran on nothing and **ate whole faces, at some viewing angles and not others**. Not one mesh in this project had tangents; it only surfaced when POM was switched on. Diagnosed first on the buttress and wrongly pinned on UV handedness (its faces were mirrored *and* untangented, and both were changed at once); the wall sweep proved it — measured 320 tangents of which **160 mirrored (w = −1)**, and adding the tangents alone fixed walls, stairs, posts and slabs. **Unity's `RecalculateTangents` encodes handedness in `tangent.w`, so mirrored UVs are fine once tangents exist** — uniform handedness is housekeeping, the tangent stream is the requirement. The five sites: `WallEdge.BuildSectionMesh` (walls AND stairs, which borrow the sweep), `WallNode.BuildWedgeMesh` ×2, `SlabTile.BuildPrism`, `Bridge.BuildMesh`, `WallButtress.BuildPrism`.
- **A georeference marker must never be solid** (2026-08-16): `CastleSite` disables its own colliders in `Awake` (play mode only — edit mode keeps them, which is what makes the marker selectable in the Scene view). The scene authored the three sites as boxes and `Start` re-seats each on the terrain at ground + 15m, so its 6×30×6m volume covers EVERYTHING at the castle centre from the ground up; the colliders outlived their renderers being hidden, leaving invisible solids that swallow the wall tools' first hit and stop the walker dead. Measured: **11 of 12 stairs climbable with the markers solid, 12 of 12 inert** — it blocks exactly the one flight crossing the site footprint, not stairs in general (the first claim here said 0 of 12, from a probe that happened to start on that one flight; scale a finding to what was actually measured). Anything else added as an editor handle owes the same guard.
- Section meshes are watertight only because neighbors evaluate the same curve at the same boundary parameter from one shared arc table. Section `tStart/tEnd` always lie in [0,1] now — the extended-arc machinery died with end extensions; edges cap flat exactly ON their node points.
- Section meshes are runtime-owned (`ownedMesh`, destroyed with the section). Preview meshes are preview-owned and always destroyed on rebuild/cancel — commit rebuilds fresh through the graph (no ownership transfer anymore).
- Colliders exist for cursor raycasts only (targeting, building on a wall top, delete) — never for occupancy.

## Input arbitration

- The scroll wheel has four meanings: camera dolly (default), Ctrl = the tool in hand's dial (wall height for the wall-family tools; path width / brush radius in the Ground tool; the PLANE in quarter steps in Foundation; the CLIMB in Stair; the pier HEIGHT in Buttress — Floor has no dial, a wall top states its plane), curve bulge (bend phase), offset distance (Offset tool with a source selected). The last two claim the wheel via `GridPlacementSystem.ClaimingScrollWheel`; `FreeFlyCamera` checks it and Ctrl before dollying — any new wheel use must join this arbitration.
- **The right mouse button has two meanings, split by travel** (2026-08-09): a right-DRAG (>4px) is camera orbit; a clean right-CLICK is UNDO — tracked centrally per frame (`rightClick`, ignored over UI), consumed by whatever chain gesture is live (slab corner, room leg, wall chain leg) and by the Delete tool (whole-world snapshot restore, below). Any new chaining gesture should honour it, through the same central tracker.
- **Never `Mathf.Round` a value onto a grid** whose ties are reachable — it's banker's rounding (ties-to-even), and the height dial's min-clamp (0.875m) sits exactly on a quarter-grid half-tie, which made alternate notches jump 0.5m. The convention is round-half-up: `Mathf.Floor(x + 0.5f)` (`CurrentWallHeight`, `HandleStairRiseScroll`).
- **The HUD's modifier panel (top right) is generated from `GridPlacementSystem.ModifierHints`**, which reports the keys the tool in hand reads *in its current phase* (wall hover/drag, curved drag/bend, circle anchor/radius, rect anchor/side/width, room chaining, delete, offset pick/placing, stair, door, ground path/restore, foundation, floor). Adding or moving a modifier means editing that method in the same commit — a panel that lists a key which does nothing is worse than no panel. Keys deliberately NOT listed where they do nothing: Shift in the curved drag, R outside the straight-build hover / the stair, Ctrl+scroll in Door / Floor (nothing is dialable there — the wall answers everything; Stair dials its climb now). The cutaway's `PgUp`/`PgDn`/`Home` are deliberately absent too: that panel reports what the *tool* reads, and the cutaway is a view control like the camera, so it carries its own keys in its own readout.
- No trigger colliders exist in the build scene, but raycast/overlap code still filters `isTrigger` — keep those filters when adding new triggers, or placement targeting will misread them.

## Tooling gotchas

- `manage_texture`'s `set_import_settings` MCP action silently drops its payload — set import settings via `execute_code` (editor API) or hand-edit the `.meta`.
- **`execute_code` that builds objects and then physics-tests them in the SAME call gets unsynced colliders** — the body walks through everything. Split across calls, or `Physics.SyncTransforms()` first.
- After script edits: `refresh_unity` (compile) + `read_console` for errors before proceeding; play-mode `execute_code` tests that delete-then-rebuild must use `DestroyImmediate` (deferred `Destroy` races validation).
- **`WallEdge.All` / `WallNode.All` are unreliable after a MID-PLAY RECOMPILE** (2026-08-17): a domain reload clears the statics and `OnEnable` does not re-fire for objects that were already enabled, so a registry can read EMPTY while 112 of the things are sitting in the scene. It bit a diagnostic probe, which reported a player's joint merlons as lost when all 15 were standing — scale a finding to what was actually measured, and in any probe run after a recompile use `FindObjectsByType` rather than the registry.
- **The wall graph is play-mode only.** `WallEdge`/`WallNode`/`SlabTile` register in `OnEnable`, which Unity doesn't call in edit mode (no `[ExecuteAlways]`), so an edit-mode `execute_code` test builds unregistered objects: `FindAt` never shares nodes, no ring ever traces, and teardown that iterates `WallEdge.All` deletes **nothing** — the orphans stay in the scene and break the next run. Test in play mode; if you must clean edit-mode litter, scan with `FindObjectsByType`.
